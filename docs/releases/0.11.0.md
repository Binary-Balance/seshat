# Seshat 0.11.0

Prepared for publication. Release preparation and verification are tracked in
[#249](https://github.com/Binary-Balance/seshat/issues/249).

## Set mutant time limits from baseline duration

Mutant jobs in both mutation phases now stop at
`min(timeoutMs, max(slowest baseline × mutantTimeoutFactor, mutantTimeoutMinMs))`.
The slowest baseline is the longest of each setup's original and worker
baselines. The two new optional per-setup settings default to 5 and 30,000,
so with the default `timeoutMs` every limit is unchanged. A setup that raised
`timeoutMs` now stops each mutant at this limit. Hanging mutants end sooner,
but a slow mutant that used to finish becomes `timed-out`, which withholds the
score and exits 2. To keep the old wait, set `mutantTimeoutMinMs` to the
`timeoutMs` value.
Typecheck, baseline and coverage jobs keep `timeoutMs`. Each `result.setups` row reports the limit its
mutant jobs used as `mutantTimeoutMs`, or `null` when none ran, and the
terminal report prints it next to each mutant that reached it. See
[mutant time limits](../configuration.md#mutant-time-limits). This resolves
[#202](https://github.com/Binary-Balance/seshat/issues/202).

## Count clean deadlines at the mutant limit as detected

With `countTimeoutsAsKilled: true`, a mutant job deadline now counts as
detected when the job ran to its setup's mutant limit and Seshat stopped the
process tree cleanly. A synchronous endless loop, which the runner's own test
timer cannot stop, no longer withholds the score. Extreme mutants follow the
same rule. Reports keep the `timed-out` verdict and `timedOut: true`, and add
counted deadlines to `countedTimeouts`. Baseline and coverage deadlines never
count. Without the opt-in, mutant job deadlines stay unresolved.

This applies to existing configurations. A slow mutant that reaches the limit
also counts as detected, even if it would have survived. To give slow mutants
longer, raise `mutantTimeoutMinMs` and `timeoutMs` together.

A deadline that `timeoutMs` cut short before the derived limit still stays
unresolved. This includes the default 30,000 when the slowest baseline is over
6 s. That setup's `result.setups` row then reports the derived limit as
`uncappedMutantTimeoutMs`, which is otherwise `null`, and the terminal report
prints one line for the setup saying which `timeoutMs` would let it count.

With the opt-in and a raised `timeoutMs`, a slow test whose runner timeout used
to fire first and count can now reach the lower mutant limit first. That
deadline still counts when it stops cleanly. The terminal report now says
"Timeouts counted as killed" instead of "Runner-reported timeouts counted as
killed".

With the opt-in, `countedTimeouts` can now include job deadlines, and these are
not in `unresolvedBreakdown.testTimedOut`. So `testTimedOut - countedTimeouts`
no longer gives the uncounted runner-reported timeouts. Subtract only counted
outcomes that have no `timedOut: true` setup; see the
[report format](../report-format.md#mutation-assessment). See also the
[timeout policy](../configuration.md#count-timeouts-as-detected). This resolves
[#240](https://github.com/Binary-Balance/seshat/issues/240).

## Skip zero-coverage jobs per setup

A setup whose complete coverage proves it never executes a mutant's source now
skips that mutant's job and records `no-coverage`, while other setups still
run. Previously every setup had to prove zero coverage, so a project with unit
and integration setups often ran both jobs for each mutant. Verdicts are
unchanged. Module-level mutants and setups without complete attribution still
run their commands. This resolves
[#227](https://github.com/Binary-Balance/seshat/issues/227).

## Share worker copies across mutation phases

With `workers` above one, Seshat now copies the project and runs each worker's
baselines once, before the extreme phase, and both mutation phases reuse those
copies. Previously each phase made its own copies and baselines. Verdicts are
unchanged in a run whose worker baselines pass. Without switching, `jobsAttempted` no longer includes a second set
of worker baselines. `result.mutation` reports the shared `workerBaselineJobs`,
`workerBaselines`, `workerPreparationMs` and `workerCleanupMs`;
`result.pseudoTesting` reports no worker baselines. `executionMs` in both
phases no longer includes worker copies and their baselines, so it falls
compared with 0.10.0. `workerBaselineJobs` can now exceed
`(workersUsed - 1) × setups`. A failed worker copy or
baseline now stops both phases. With switching, each worker still runs a
prepared baseline before the operator phase, so switching saves the copies but
not those baselines. This resolves
[#221](https://github.com/Binary-Balance/seshat/issues/221).

## Skip a repeated TypeScript check

A direct `tsc` typecheck no longer runs when the compiler findings helper has
already checked the same program without errors and `noEmit` is set. Reports
record this as `setups[].typecheck.reusedFrom: "compilerStrictness"`, with
`state: "passed"` and no `exit` or `ms`. Its `timings.typecheckMs` stays `null`,
and it adds nothing to `jobsAttempted`. This resolves [#222](https://github.com/Binary-Balance/seshat/issues/222).

## Release packages and checks

The prepared package set is `@binary-balance/seshat@0.11.0` with exact-version
native payloads for Linux x64, Linux ARM64, macOS x64, macOS ARM64 and Windows x64.
The [platform support matrix](../platform-support.md) is unchanged.

The [archive and notice audit](../research/release-notice-audit.md) records the
six exact archive hashes, native proofs and Windows runtime evidence for
reviewed build head `394afba477bb974f0fb74103186a22d0644f0eef` in
[PR #250](https://github.com/Binary-Balance/seshat/pull/250). Release inputs
merged at `bcc0f95a67d1f49b70ee51424f72e265226abee1` with matching
`crates`, `packages` and `packaging` source trees.

All five native package targets and the Windows runtime proof passed:

- [Linux x64](https://github.com/Binary-Balance/seshat/actions/runs/41187182223)
- [Linux ARM64](https://github.com/Binary-Balance/seshat/actions/runs/41187182290)
- [macOS x64 and ARM64](https://github.com/Binary-Balance/seshat/actions/runs/41187182250)
- [Windows x64](https://github.com/Binary-Balance/seshat/actions/runs/41187182235)
- [Windows runtime](https://github.com/Binary-Balance/seshat/actions/runs/41187182262)

Compared with the audited 0.10.0 archive, all 65 dependency records, Rust 1.98.1
and runtime notice assets are unchanged. The notice file is byte-identical on
all five targets and to 0.10.0. The published 0.10.0 audit is preserved unchanged
as [JSON](0.10.0-audit.json) and [Markdown](0.10.0-audit.md).

On all five hosts, the 51 mutant and pseudo-test outcomes from the public
examples and the Vitest and Jest/Expo checks, their scores and
`workerBaselineJobs` match the 0.10.0 build. `jobsAttempted` falls by one in each
of those 12 reports because the direct `tsc` job no longer runs
([#222](https://github.com/Binary-Balance/seshat/issues/222)). These reports do
not exercise the savings from
[#221](https://github.com/Binary-Balance/seshat/issues/221) and
[#227](https://github.com/Binary-Balance/seshat/issues/227).

One fault-injection scenario changes. In `worker-baseline-error`, the extreme
mutant goes from `killed` to `not-run`, because a failed worker baseline now
stops both phases (#221). That run was already incomplete in 0.10.0. All other
existing proof outcomes are unchanged. The [verdict evidence](../research/fewer-jobs-verdicts.md)
lists them with job counts and phase timings.

The read-only stager verified the six canonical archives against their audited
byte counts and SHA-256 hashes. Five-host local installation checks and the final
publisher dry run remain pending. npm publication requires approval of the exact
prepared release under the [publication checkpoint](../agents/delivery.md#npm-publication-checkpoint).
